# 录制操作节点设计

日期：2026-10-28
状态：已确认（2026-10-28）

## 目标

新增一种“录制操作”步骤：用户在检查器里点击“录制操作”，打开一个带实时手机画面的录制窗口；在窗口里用触摸手势操作手机。第一次输入开始计时，最后一次输入结束计时；录制完成后保存成步骤内容。运行时到达该步骤，立刻执行第一次输入，按录制时的相对时间回放后续操作，最后一次输入执行完即进入下一步。

## 非目标

- 不做键盘文本输入、硬件按键、多点触控/双指缩放。
- 不做 scrcpy 式实时跟手控制；滑动等手势在松手后通过 ADB 发送，已确认可接受。
- 不做逐条动作编辑、裁剪、暂停续录；只能整段重录或清除。
- 不做服务端录制会话、断线恢复或跨客户端同步。
- 不改变现有实时投屏窗口的只读行为；录制窗口是独立的覆盖式弹窗。
- 旧 Tkinter 桌面界面不作为本次支持目标，网页工作台优先。

## 用户流程

1. 从步骤库添加“录制操作”节点，或选中已有节点。
2. 检查器显示“尚未录制”和“录制操作”按钮；点击后打开录制窗口。
3. 窗口连接实时投屏，等待第一次输入；第一次输入前等待多久都不计时。
4. 用户点击、长按、拖动；每次手势都会通过 ADB 输入到手机，并加入动作列表。
5. 最后一次输入结束后点击“完成录制”；最后输入到点击按钮之间的空档不保存。
6. 节点保存动作列表和录制时的设备分辨率；检查器显示“N 个操作 · X 秒”。
7. 运行时到达该节点，第一次动作立即执行；按相对时间等待并执行后续动作；最后一个动作结束即完成。

## 数据模型

步骤类型：`recorded_actions`，标签“录制操作”。

```json
{
  "kind": "recorded_actions",
  "params": {
    "actions": [
      {"type": "tap", "x": 320, "y": 640, "at": 0},
      {"type": "swipe", "x1": 320, "y1": 640, "x2": 320, "y2": 1200,
       "duration": 380, "at": 1250}
    ]
  },
  "screen_resolution": {"width": 1080, "height": 2400}
}
```

- `at`：相对第一次输入开始的时间，整数毫秒，第一条为 0，后续非递减。
- `tap`：`x`、`y` 为原始设备像素。
- `swipe`：起终点为原始设备像素，`duration` 为按住/滑动时长（毫秒）；长按用起终点相同的 swipe 表示。
- `actions` 允许为空（新建但尚未录制的节点）；运行到空动作节点会失败并提示“尚未录制操作”。
- 单节点最多 1000 条动作；单次手势时长 1–5000 毫秒。
- 录制完成时写入 `screen_resolution`；预设包导入/适配分辨率时按该分辨率缩放动作坐标。

## 录制规则

- 使用 `performance.now()` 计时；第一次**提交成功的手势**的按下时间作为原点。
- 第一次输入前的等待完全丢弃；第一次动作的 `at` 为 0。
- 点击：移动距离小于 8 设备像素且按住时间小于 500ms。
- 长按：移动距离小于 8 设备像素且按住时间至少 500ms；保存为起终点相同的 swipe，时长等于按住时间。
- 滑动：移动距离至少 8 设备像素；`duration` 为按下到松开的时长。
- 下一次动作的 `at` 是它自己的按下时间减去原点；动作之间的等待原样保留。
- 最后一次动作结束（tap 为按下时刻，swipe 为 `at + duration`）即录制内容结束；之后到点击“完成录制”的等待不保存。
- 没有动作时不能完成；点击“完成录制”给出提示。
- 取消或关闭窗口丢弃本次录制；已有动作时先确认。
- 录制中途设备分辨率变化时停止接受输入并提示取消后重录，避免坐标错位。
- 手势先加入动作列表，再按顺序排队发送输入，避免快速操作时 ADB 命令乱序；完成录制前等待队列清空。
- 某次输入发送失败时显示错误并暂停接受新手势；已记录的动作保留，用户可以取消，或在确认提示后完成录制。播放阶段仍可重试这些已记录动作。

## 回放规则

- 空动作列表：失败“尚未录制操作”。
- 对每条动作，先等待 `max(0, at - 上一条结束时间)` 秒，使用可中断的 `RuntimeContext.wait`。
- tap 调 `context.device.tap(x, y)`；swipe 调 `context.device.swipe(x1, y1, x2, y2, duration)`。
- 上一条结束时间：tap 为 `at`，swipe 为 `at + duration`。
- 第一条 `at=0`，所以到达节点后立即执行第一次输入。
- 最后一条执行完立即返回成功，不追加尾部等待。
- 每条动作前检查停止请求；停止时返回 stopped。
- 设备错误按普通步骤失败处理；不做运行时自动缩放，分辨率不匹配时由检查器提示并调用现有“适配”。

## 录制窗口

- 覆盖式弹窗，复用 `useDeviceStream`，不单独开浏览器窗口，也不改动现有只读手机画面窗口。
- 打开前要求设备已连接且已取得原始分辨率；否则在检查器提示先连接/检测设备，不打开窗口。
- 布局：顶部标题和关闭；左侧/中间手机画面；右侧动作列表；底部取消和完成录制。
- 手机画面使用 `object-fit: contain`；透明指针层覆盖画面，按画面实际渲染矩形把浏览器坐标映射到原始设备分辨率。
- 画面未就绪或投屏错误时禁用指针层，显示重试/错误状态。
- 动作列表显示序号、类型、坐标、相对时间；显示“已录制 N 个操作 · X 秒”。
- 首次输入前状态为“等待第一次输入”；首次提交后变为“录制中”。
- “完成录制”在没有动作或仍在等待输入队列时禁用；完成后把动作交给检查器。
- 录制期间通过 `uiStore.recordingOpen` 阻止全局快捷键（保存、撤销、删除等）和画布编辑。

## 反向输入

新增 `POST /api/device/input`：

```json
{"type": "tap", "x": 320, "y": 640, "serial": "设备序列号"}
{"type": "swipe", "x1": 320, "y1": 640, "x2": 320, "y2": 1200,
 "duration": 380, "serial": "设备序列号"}
```

- `serial` 可选但推荐；录制窗口打开时捕获当前设备序列号，并在每条输入里携带。
- 有 `serial` 时后端直接对该序列执行，不改变当前选择、也不回退到其他设备；没有 `serial` 时使用当前选中设备或单设备默认行为。
- 校验类型、整数坐标、时长（1–5000ms）；非法返回 400。
- 使用 `RuntimeManager.mutation()` 与运行准入互斥；正在运行时返回 409。
- 设备命令失败映射为 503；成功返回 `{"ok": true}`，不附带设备目录等慢操作。
- 输入请求不持久化、不进入运行日志；录制动作只保存在前端步骤参数中。

## 方案

### A. 浏览器端录制 + 新步骤类型 + ADB 输入接口（选用）

动作时间线在浏览器采集，步骤参数保存动作，ADB 输入接口负责即时反向控制，执行引擎负责回放。

- 优点：不新增服务端录制会话或文件；与现有配置快照、撤销、预设包、执行状态一致。
- 代价：滑动松手后才执行；每条输入一次 HTTP/ADB 调用；前端需要处理计时与坐标映射。

### B. 复用现有悬浮手机画面，增加控制和录制模式（未选用）

少一个窗口，但只读监视和编辑录制混在一起，悬浮窗几何、坐标映射、状态切换和误操作都更复杂。

### C. 后端录制会话（未选用）

前端只发指针事件，后端维护会话并在完成时提交动作。校验集中，但新增会话生命周期、并发和清理，收益不大。

## 风险与边界

- 回放时间精度受浏览器、HTTP、ADB 延迟影响；`at` 只保证相对等待，不保证毫秒级同步。
- 单指录制；双指缩放、键盘和硬件键不会记录。
- 长按用同点 swipe 表示，依赖 Android `input swipe` 的触摸语义。
- 录制期间切换设备会破坏画面和输入目标；界面阻止切换，输入接口按序列号拒绝回退。
- 设备旋转/分辨率变化会停止录制，要求重录。
- 动作数量上限和单次手势时长上限防止配置过大和 ADB 命令超时。
- Tkinter 桌面界面不提供该节点的录制界面。
